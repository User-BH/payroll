# سامانه حقوق و دستمزد — تامین کالا باختر

نسخهٔ دمو. Django + HTMX + Alpine.js + MySQL، تمام‌فارسی و RTL.

> **هشدار مهم:** همهٔ اعداد قانونی (حداقل دستمزد، حق مسکن، بن، پلکان مالیات، نرخ بیمه)
> **داده نمونه** هستند و باید پیش از استفادهٔ واقعی با بخشنامه‌های سال تطبیق داده شوند.
> جای همه‌شان در «تنظیمات سال مالی» است و هیچ‌کدام در کد نوشته نشده‌اند.

---

## دیتابیس: فقط MySQL 8

سامانه روی هیچ موتور دیگری اجرا نمی‌شود — نه در توسعه، نه در تولید. دلیلش این است
که رفتار دیتابیس دقیقاً در جاهایی که برای حقوق و دستمزد حیاتی است بین موتورها فرق
دارد: پشتیبانی از قیدهای یکتایی، دقت `DECIMAL`، حالت `STRICT` و کولیشن فارسی. اگر
روی یک موتور توسعه بدهیم و روی موتور دیگری اجرا کنیم، این تفاوت‌ها را دیر و روی
دادهٔ واقعی حقوق کشف می‌کنیم.

> نمونهٔ واقعی همین موضوع: قید «هر پرسنل در هر دوره فقط یک فیش اصلی» ابتدا با
> `UniqueConstraint(condition=...)` نوشته شده بود. MySQL ایندکس شرطی ندارد و جنگو
> چنین قیدی را **بی‌صدا نادیده می‌گیرد**. حالا با ستون `revision` نوشته شده تا قید
> واقعاً در دیتابیس اعمال شود.

## اجرای محلی

```bash
docker run -d --name payroll-mysql \
  -e MYSQL_ROOT_PASSWORD=rootpw -e MYSQL_DATABASE=payroll \
  -e MYSQL_USER=payroll -e MYSQL_PASSWORD=payrollpw \
  -p 3307:3306 mysql:8 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_persian_ci
```

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # DB_PORT=3307 و DB_PASSWORD=payrollpw
python manage.py migrate
python manage.py seed_demo
python manage.py runserver
```

سپس <http://127.0.0.1:8000>

## راه‌اندازی روی سرور لینوکس با MySQL

### ۱. پیش‌نیازها

```bash
sudo apt update
sudo apt install -y python3-venv python3-dev build-essential pkg-config \
                    default-libmysqlclient-dev mysql-server nginx
```

### ۲. ساخت دیتابیس

کولیشن `utf8mb4_persian_ci` برای مرتب‌سازی درست فارسی لازم است:

```bash
sudo mysql -e "CREATE DATABASE payroll CHARACTER SET utf8mb4 COLLATE utf8mb4_persian_ci;"
sudo mysql -e "CREATE USER 'payroll'@'localhost' IDENTIFIED BY 'CHANGE_ME';"
sudo mysql -e "GRANT ALL PRIVILEGES ON payroll.* TO 'payroll'@'localhost'; FLUSH PRIVILEGES;"
```

### ۳. گرفتن کد از گیت‌هاب

```bash
sudo mkdir -p /srv/payroll && sudo chown $USER /srv/payroll
git clone https://github.com/User-BH/payroll.git /srv/payroll
cd /srv/payroll
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

### به‌روزرسانی‌های بعدی

```bash
sudo bash /srv/payroll/deploy/update.sh
```

این اسکریپت به ترتیب: **بکاپ دیتابیس و فایل‌های آپلودی** → `git pull` →
نصب وابستگی‌ها → `migrate` → `collectstatic` → تنظیم دسترسی پوشه `media` →
ری‌استارت سرویس → `doctor`.

بکاپ اول از همه گرفته می‌شود چون `migrate` برگشت‌پذیر نیست. اگر هر قدم شکست
بخورد، اسکریپت همان‌جا متوقف می‌شود و مسیر فایل بکاپ را برای بازگردانی چاپ
می‌کند. ۱۴ بکاپ آخر نگه داشته می‌شوند.

اگر روی سرور فایلی را دستی تغییر داده باشید، اسکریپت قبل از `git pull` متوقف
می‌شود و تغییرات را نشان می‌دهد تا ناخواسته پاک نشوند.

### بررسی سلامت نصب

هر وقت چیزی کار نکرد، اول این را اجرا کنید:

```bash
python manage.py doctor
```

اتصال دیتابیس، کولیشن، تعداد جدول‌ها، وجود کاربر، `DEBUG`، `ALLOWED_HOSTS`،
`SECURE_COOKIES`، `SECRET_KEY` و `collectstatic` را بررسی می‌کند و برای هر ایراد
دقیقاً می‌گوید چه دستوری را اجرا کنید.

### ۶. سرویس systemd

فایل آماده در `deploy/systemd/payroll.service` است:

```bash
sudo cp deploy/systemd/payroll.service /etc/systemd/system/
sudo chown -R www-data:www-data /srv/payroll
sudo systemctl daemon-reload && sudo systemctl enable --now payroll
sudo systemctl status payroll --no-pager
```

### ۷. nginx

فایل آماده در `deploy/nginx/payroll.conf` است:

```bash
sudo cp deploy/nginx/payroll.conf /etc/nginx/sites-available/payroll
sudo ln -sf /etc/nginx/sites-available/payroll /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

nginx باید بتواند وارد مسیر شود تا فایل‌های استاتیک را بخواند:

```bash
sudo chmod o+x /srv /srv/payroll
```

**سایت `default` را کورکورانه پاک نکنید.** اگر روی این سرور سایت دیگری هم هست،
حذفش آن‌ها را می‌خواباند. کانفیگ ما با `server_name` کار می‌کند و با بقیه‌ی
سایت‌ها تداخلی ندارد. `default` را فقط وقتی غیرفعال کنید که مطمئنید سایت دیگری
به آن وابسته نیست:

```bash
sudo ls -l /etc/nginx/sites-enabled/          # اول ببینید چه چیزی فعال است
sudo rm /etc/nginx/sites-enabled/default      # فقط در صورت اطمینان
```

اگر دامنه به سایت اشتباهی می‌رسد، ببینید nginx کدام بلوک را برای آن انتخاب می‌کند:

```bash
sudo nginx -T | grep -n "server_name"
```

## سه اصل معماری

۱. **هیچ داده‌ای «جاری» نیست.** حقوق پایه روی `EmploymentContract` تاریخ‌دار است، نه روی
   `Employee`. هر ترفیع یا تغییر واحد = یک قرارداد جدید با `effective_from` جدید.

۲. **فیش قفل‌شده تغییرناپذیر است.** لحظهٔ محاسبه، کل پارامترهای قانونی داخل
   `Payslip.params_snapshot` کپی می‌شوند. `Payslip.save()` نوشتن روی فیشِ دورهٔ قفل‌شده
   را رد می‌کند.

۳. **هر عدد توضیح خودش را دارد.** `PayslipLine.explanation` مثلاً:
   «اضافه‌کاری: ۳۳ ساعت × ۱٬۱۱۴٬۱۴۳ ریال مزد ساعتی × ۱٫۴».

### موتور محاسبه

منطق در کد است، نه در دیتابیس. هر قلم حقوقی به یک قاعدهٔ ثبت‌شده در
`apps/payroll/engine/rules.py` وصل می‌شود (`engine_rule_key`)؛ دیتابیس فقط ضریب،
ترتیب و شمول بیمه/مالیات را نگه می‌دارد.

اجرا چهار پاس دارد: **مزایا → کسور → هزینهٔ کارفرما → مبناهای اطلاعی**. دلیل
سه پاس اول این است که **مبنای بیمه و مبنای مالیات دو عدد جدا هستند**؛ اگر بیمه و
مالیات هم‌زمان با مزایا محاسبه می‌شدند، ترتیب اقلام روی نتیجه اثر می‌گذاشت. در
دادهٔ نمونه، پورسانت فروش مشمول مالیات و معاف از بیمه است و همین تفاوت را نشان
می‌دهد.

پاس چهارم اقلام `INFO` است — ماخذ بیمه، ماخذ مالیات، مزد روزانه، مزد ساعتی،
جمع ناخالص و کل هزینهٔ کارفرما. این‌ها پرداختی نیستند و در هیچ جمعی وارد
نمی‌شوند؛ فقط نشان می‌دهند هر محاسبه روی چه عددی نشسته است.

افزودن یک قلم جدید:

```python
@rule("my_rule", "عنوان")
def my_rule(ctx, component):
    return LineResult(
        amount=...,
        base_amount=..., quantity=..., rate=...,
        explanation="…",
    ).rounded()
```

## آنچه در این نسخه هست

داشبورد · پرسنل و تاریخچهٔ قرارداد · دوره و ماشین حالت آن · کارکرد ماهانه با ویرایش
درجا (HTMX) · موتور محاسبه · فیش با ریز محاسبات و نسخهٔ چاپی · اقلام حقوقی ·
تنظیمات سال مالی · گزارش بیمه/مالیات/بانک با خروجی اکسل · پرتال کارکنان.

### افزودن پرسنل

یک صفحه، یک بار ذخیره: **اطلاعات هویتی · نوع قرارداد و کارکرد · حساب بانکی.**
رفتن به بخش دیگر برای دو فیلد، کار ساده را چندمرحله‌ای می‌کند.

فرم فقط **نوع قرارداد** را می‌پرسد، نه ریز جزئیات قرارداد را. با
ذخیره، یک قرارداد **فعال** از تاریخ استخدام ساخته می‌شود تا پرسنل بلافاصله در
فهرست فعال باشد و بشود رویش کلیک کرد، ویرایشش کرد و خروجش را ثبت کرد.

واحد، مرکز هزینه و پست سازمانی از اولین مقدارِ ساختار سازمانی پر می‌شوند و
**حقوق پایه صفر** می‌ماند — عددِ حدسی برای حقوق، اشتباهی است که تا فیش پنهان
می‌ماند، ولی صفر در همان صفحهٔ پرسنل با هشدار دیده می‌شود. تکمیلش از دکمهٔ
«ویرایش قرارداد» انجام می‌شود.

اگر دورهٔ پیش‌نویسی باز باشد، همان‌جا **کارکرد ماهانه** هم قابل ثبت است. بعد از
ثبت هم، پنل «کارکرد ماهانه» در صفحهٔ خود پرسنل اجازهٔ ورود دستی می‌دهد — بدون
باز کردن جدول کارکرد کل دوره. هر دو مسیر روی همان یک رکورد `Timesheet` می‌نویسند.

### کارکرد ماهانه

ورودی‌های هر ردیف: روز کارکرد · مرخصی استحقاقی · غیبت · مرخصی بدون حقوق ·
حق مأموریت (روز) · اضافه‌کاری · تعطیل‌کاری.

**مرخصی و اضافه‌کاری هر دو سه ورودی دارند — از راست: دقیقه، ساعت، روز.** مبنای
ذخیره در هر دو **دقیقه** است (`leave_minutes` و `overtime_minutes`)؛ روزِ اعشاری
و ساعتِ اعشاری همیشه از روی دقیقه ساخته می‌شوند، نه برعکس، وگرنه خطای گرد کردن
جمع می‌شود. طول یک روز کاری از `LegalParameter.leave_day_minutes` می‌آید
(پیش‌فرض ۴۴۰ دقیقه = ۷ ساعت و ۲۰ دقیقه) و برای هر دو یکی است.

**ستون‌های این جدول داده‌اند، نه کد.** فهرستشان در «تنظیمات ← اقلام کارکرد»
است و هر کدام یک واحد دارد (روز، ساعت یا دقیقه). شب‌کاری، جمعه‌کاری و
تعطیل‌کاری تعریف شده ولی خاموش‌اند، چون فیش‌های فعلی شرکت چنین قلمی ندارند؛ با
یک دکمه در همان صفحه به جدول کارکرد برمی‌گردند.

برای اینکه یک ستون کارکرد به **مبلغ** تبدیل شود، یک قلم حقوقی لازم است که
«نحوه محاسبه»‌اش قاعدهٔ پارامتری و «مقدار»ش همان قلم کارکرد باشد. مثلاً
جمعه‌کاری:

```
ستون  «جمعه‌کاری»  واحد ساعت            ← تنظیمات / اقلام کارکرد
قلم   «جمعه‌کاری» = مزد روزانه × ساعت جمعه‌کاری × ۰٫۴   ← تنظیمات / اقلام حقوقی
```

هیچ کدی لازم نیست؛ همین برای هر قلم تازهٔ دیگری هم هست. هفت ستون اول جدول
(کارکرد، مرخصی، غیبت، بیماری، مرخصی بدون حقوق، مأموریت، اضافه‌کاری) ویجت
اختصاصی خودشان را دارند و همیشه در جدول هستند.

### کارتابل مرخصی

`/leave/desk/` جایی است که کارگزینی مرخصی را **یک بار** ثبت می‌کند و همان لحظه در
کارکرد همان ماه می‌نشیند — بدون ورود دوباره در جدول کارکرد.

هر رکورد `LeaveRecord` سه چیز دارد: نوع (استحقاقی / بدون حقوق / استعلاجی)، بازهٔ
تاریخ، و مدت به **دقیقه** (ورودی به‌صورت روز/ساعت/دقیقه، از راست همان ترتیب جدول
کارکرد).

**قاعدهٔ همگام‌سازی — تنها جای تصمیم، `apps/attendance/leave_desk.py`:**

> اگر برای یک نوع مرخصی در آن دوره رکوردی وجود داشته باشد — ثبت‌شده یا لغوشده —
> آن ستونِ کارکرد از **جمع رکوردهای ثبت‌شده** ساخته می‌شود، حتی اگر آن جمع صفر
> باشد. نوعی که هیچ رکوردی ندارد دست‌نخورده می‌ماند.

سه نتیجهٔ مستقیم از همین یک جمله:

- کارتابل روی عددی که کاربر دستی در جدول کارکرد زده دست نمی‌اندازد، مگر برای
  نوعی که واقعاً در کارتابل ثبت شده باشد. غیبتِ دستی سر جایش می‌ماند.
- چون هر بار از صفر جمع می‌زند، ثبت و ویرایش مکرر هرگز دوباره‌شماری نمی‌کند.
- لغو، سهم رکورد را همان لحظه از ستون برمی‌دارد؛ لغوِ تنها رکورد بیماری یعنی
  ستون بیماری صفر می‌شود، نه اینکه عدد قبلی جا بماند.

**مرخصی روی مرز دو ماه** به نسبت روز بین دوره‌ها تقسیم می‌شود
(`LeaveRecord.minutes_in()`) و جمع سهم‌ها دقیقاً برابر کل رکورد می‌ماند — چهار روز
مرخصی که یک روزش در اسفند و سه روزش در فروردین است، ۴۴۰ + ۱۳۲۰ دقیقه می‌شود.

**دورهٔ قفل‌شده دست نمی‌خورد.** ثبت مرخصی برای ماهی که محاسبه یا قفل شده کارکرد را
عوض نمی‌کند و پیام همین را می‌گوید؛ سه حالتِ «اعمال شد»، «دوره قفل است» و «هنوز
دوره‌ای برای این تاریخ نیست» از هم جدا گزارش می‌شوند. دکمهٔ «اعمال دوباره در کارکرد»
یک دورهٔ باز را از روی کل کارتابل بازسازی می‌کند.

**مانده مرخصی** جای جدایی ندارد: `compute_balance()` از جمع `leave_minutes` همان
سال می‌آید، پس به‌روز شدن کارکرد یعنی به‌روز شدن مانده. هیچ عددِ ماندهٔ ذخیره‌شده‌ای
وجود ندارد که با کارتابل ناهماهنگ شود.

### کارکرد اولیه و کارکرد قابل پرداخت

زنجیرهٔ محاسبهٔ حقوق ثابت:

```
کارکرد اولیه (از تاریخ استخدام / خاتمه کار / شروع به کار مجدد)
  − غیبت − بیماری − مرخصی بدون حقوق
  = کارکرد قابل پرداخت
  × مزد روزانه (دستمزد قرارداد، وگرنه حداقل دستمزد سال)
  = حقوق ثابت
```

**کارکرد اولیه** طول اشتغال همان پرسنل در همان ماه است، نه طول کامل ماه.
`Employee.employed_days_in()` آن را از تقاطع بازهٔ اشتغال با بازهٔ دوره حساب
می‌کند. **خودِ تاریخ خاتمه کار جزو کارکرد نیست:** خاتمهٔ ۱۶ مرداد یعنی آخرین
روز کارکرد ۱۵ مرداد، پس کارکرد اولیه ۱۵ روز است نه ۳۱.

`rehire_date` بازهٔ دوم می‌سازد: خاتمه ۱۱ مرداد و بازگشت ۲۱ مرداد یعنی
۱۰ + ۱۱ = ۲۱ روز.

**مرخصی استحقاقی و مأموریت کسر نمی‌شوند** چون پرداخت دارند و داخل کارکرد اولیه
هستند. فقط سه قلمِ بی‌حقوق کم می‌شوند.

### اقلام روزی

غیبت، بیماری و مرخصی بدون حقوق روی فیش **فقط تعداد روز** نشان می‌دهند و مبلغ
ریالی ندارند — اثر مالی‌شان قبلاً با کم شدن از کارکرد اعمال شده و مبلغ ریالی
یعنی کسر مضاعف.

این رفتار دادهٔ قلم است نه شرط کدنویسی‌شده: `SalaryComponent.display_unit` با
مقادیر ریال / روز / ساعت. سطرِ با مبلغ صفر معمولاً از فیش حذف می‌شود، ولی سطری
که واحدش ریال نیست و تعداد دارد می‌ماند.

### دستمزد واقعی و حداقل دستمزد

`EmploymentContract.base_salary` همان **دستمزد واقعی** است. خالی یا صفر یعنی
«از حداقل دستمزد همان سال استفاده کن» — نه اینکه حقوق صفر باشد.

- `min_daily_wage` روزانه است و مستقیم مزد روزانه می‌شود.
- دستمزد واقعی ماهانه است و بر **طول همان ماه** تقسیم می‌شود.

توضیح سطر «حقوق ثابت» روی فیش می‌گوید با کدام مبنا حساب شده است. اگر هر دو خالی
باشند، صفحهٔ پرسنل هشدار می‌دهد.

### روز کارکرد ماه

**۳۱ روز در شش‌ماههٔ اول، ۳۰ روز در شش‌ماههٔ دوم، و اسفند ۲۹ روز (در سال کبیسه
۳۰).** این عدد از تقویم خودِ دوره خوانده می‌شود (`PayrollPeriod.month_days`)، نه
از یک ثابت.

دو جا اثر دارد: **مقدار پیش‌فرضِ** «روز کارکرد» هنگام ساخت ردیف‌های کارکرد، و
**مخرجِ محاسبه** — مزد روزانه (`حقوق پایه ÷ روزهای ماه`) و تسهیم مزایای ثابت
(`روز کارکرد ÷ روزهای ماه`). عدد واقعیِ روز کارکرد هر پرسنل دستی وارد می‌شود؛
پیش‌فرض فقط نقطهٔ شروع است.

مقدار به‌کاررفته در `Payslip.params_snapshot["month_days"]` ثبت می‌شود تا فیش
قفل‌شده مخرج محاسبه‌اش را برای همیشه همراه داشته باشد.
`LegalParameter.monthly_days` فقط وقتی به کار می‌آید که دوره بازهٔ تاریخی نداشته
باشد.

### آیتم‌های سالانه و ماهانه

دو خانوادهٔ متفاوت، دو جای متفاوت:

| | کجا | مثال |
|---|---|---|
| **سالانه و ثابت** | تنظیمات سال مالی | حداقل دستمزد · پایه سنوات · حق مسکن · بن · حق اولاد |
| **ماهانه و متغیر** | آیتم‌های محاسباتی ماهانه | مبنای حق مأموریت · مبنای اضافه‌کاری · سقف روز مأموریت |

صفحهٔ **«آیتم‌های ماهانه»** (`/periods/<id>/monthly/`) برای هر دوره یک مقدار
اختیاری می‌گیرد. **خانهٔ خالی یعنی همان مقدار سال مالی** — این جدول جایگزین
تنظیمات سال نیست، استثنای همان ماه است.

ترتیب خواندن در موتور: **مقدار ماهانهٔ همان دوره، وگرنه مقدار سالانه.**

پیاده‌سازی عمداً هیچ قاعده‌ای در `rules.py` را دست نزد. لایهٔ
`EffectiveParams` (در `apps/payroll_config/monthly.py`) پارامتر سالانه را با
مقادیر ماهانه می‌پوشاند و همان نام فیلدها را برمی‌گرداند؛ قاعده‌ها همچنان
`ctx.params.housing_allowance` می‌خوانند و نمی‌دانند عدد از سال آمده یا از ماه.

`min_monthly_wage` و `insurance_ceiling` از مقادیر **مؤثر** ساخته می‌شوند، نه
سالانه — وگرنه تغییر ماهانهٔ حداقل دستمزد در سقف بیمه اثر نمی‌کرد.

مقادیر مصرف‌شده در `Payslip.params_snapshot` می‌نشینند و کلید
`monthly_overrides` می‌گوید کدام‌ها ماهانه بوده‌اند. شناسهٔ محاسبه هم مقادیر
ماهانه را در بر می‌گیرد، وگرنه دو فیشِ متفاوت یک شناسه می‌گرفتند.

فهرست کلیدهای مجاز در `apps/payroll_config/monthly.py` است. سه کلید فقط ماهانه‌اند
و روی `LegalParameter` فیلد ندارند: `mission_daily_rate`، `overtime_hourly_rate`
و `mission_max_days` (پیش‌فرض ۲۵ روز) — این‌ها زیرساخت فاز بعدی‌اند و **هیچ‌کدام
در کد ثابت نشده‌اند**.

### پورسانت، حق مأموریت و اضافه‌کاری

پورسانت طبق ضوابط شرکت می‌تواند در ردیف **حق مأموریت** یا **اضافه‌کاری** بنشیند،
ولی هر دو سقف دارند. صفحهٔ **«تخصیص پورسانت»** (`/periods/<id>/commission/`)
این تقسیم را نشان می‌دهد و اجازهٔ تغییر دستی می‌دهد.

**قانون حفظ مبلغ — همیشه برقرار است:**

```
پورسانت اولیه = منتقل‌شده به مأموریت + منتقل‌شده به اضافه‌کاری + مانده
```

مبلغی که در هیچ ظرفیتی جا نشود **حذف نمی‌شود** و به‌عنوان ماندهٔ پورسانت روی
همان قلم باقی می‌ماند. اگر پورسانت چند قلم باشد (سطح ۱، ۲، ۳)، مانده به نسبت
سهم هر قلم تقسیم می‌شود تا جمع سطرها دقیقاً برابر ماندهٔ کل بماند.

**ظرفیت یعنی ظرفیت باقی‌مانده.** مأموریت و اضافه‌کاریِ واقعیِ همان ماه (از جدول
کارکرد) اول جای خودشان را می‌گیرند و پورسانت فقط فضای خالی را پر می‌کند:

```
ظرفیت مأموریت    = مبنای روزانهٔ ماه × (سقف روز − روز مأموریت واقعی)
ظرفیت اضافه‌کاری = مبنای ساعتی ماه × (سقف ساعت − ساعت اضافه‌کاری واقعی)
```

هیچ سقفی در کد نیست؛ هر چهار عدد «آیتم محاسباتی ماهانه»اند. **سقف تعریف‌نشده
(صفر) یعنی انتقال انجام نمی‌شود، نه بی‌نهایت** — سند صریح گفته این جابه‌جایی
نباید نامحدود باشد.

وقتی «مبنای ساعتی اضافه‌کاری» برای ماه ثبت شده باشد، همان **مبلغ نهایی هر
ساعت** است و ضریب اضافه‌کاری روی آن اعمال نمی‌شود؛ وگرنه «ساعت معادلِ» مبلغ
منتقل‌شده با سقف ساعت نمی‌خواند و سقف بی‌معنا می‌شد.

`CommissionAllocation` کل مسیر را نگه می‌دارد — پورسانت اولیه، سهم مأموریت و
روز معادلش، سهم اضافه‌کاری و ساعت معادلش، مانده، و **مبناها و سقف‌های همان ماه**
— چون ماه بعد عوض می‌شوند و بدون آن‌ها محاسبهٔ این ماه قابل بازسازی نیست.

تخصیص‌های **دستی** در محاسبهٔ دوباره دست‌نخورده می‌مانند؛ تخصیص‌های خودکار
بازسازی می‌شوند چون ممکن است مبنای ماه یا مبلغ پورسانت عوض شده باشد.

### حساب بانکی

نام بانک از **فهرست بانک‌های کشور** انتخاب می‌شود (`apps/employees/banks.py`)، نه
متن آزاد: دو نامِ متفاوت برای یک بانک، فایل پرداخت و گزارش‌ها را دوتکه می‌کند.
کد بانک پرسیده نمی‌شود و از روی نام پر می‌شود.

**شماره شبا اختیاری است** — پرداخت این شرکت بر مبنای شماره حساب انجام می‌شود.
اگر پر شود، فاصله و حروف کوچک پذیرفته و نرمال می‌شود، رقم کنترلی‌اش با
استاندارد ISO 13616 کنترل می‌شود، و **روی فیش حقوقی چاپ می‌شود** (فیش A5، صفحهٔ
فیش و پرتال کارکنان). شبای غلط روی فیش چاپ می‌شود و بعداً کسی با آن پول
می‌فرستد؛ گرفتن غلط تایپی در فرم ارزان‌تر است.

فایل اکسل ورود پرسنل هم همین دو کنترل را دارد: نام بانک باید در فهرست باشد و
شبا باید رقم کنترلی درست داشته باشد.

### پرسنل بدون بیمه

تیک **«بدون بیمه»** روی پرسنل یک آیتم کنترلی در موتور محاسبه است، نه یک یادداشت
در پرونده. علتِ نداشتن بیمه یکی نیست — ممکن است بازنشسته باشد، یا خودش نخواهد
بیمه شود — پس علت در فیلد جداگانهٔ «علت نداشتن بیمه» ثبت می‌شود و روی پروندهٔ
پرسنل دیده می‌شود. برای موتور فرقی ندارد: تصمیم یکی است.

تصمیم در یک نقطه گرفته می‌شود — `PayrollContext.insurance_applies` — و هر پنج
مسیر از همان می‌آیند:

| مسیر | رفتار |
|---|---|
| اجرای دوره | سه قلم بیمه از فهرست اقلام آن پرسنل حذف می‌شوند |
| قواعد موتور | `insurance_employee` · `insurance_employer` · `unemployment_insurance` نتیجه‌ای تولید نمی‌کنند |
| فیش | هیچ ردیف بیمه‌ای ندارد |
| گزارش بیمه | نه در جدول است، نه در تعداد و جمع‌ها — با ذکر نامش در کادر هشدار |
| فایل DSK تأمین اجتماعی | نه در سطرها، نه در جمع‌ها، نه در تعداد نفرات |

شرط کامل: **قرارداد مشمول بیمه باشد و پرسنل «بدون بیمه» علامت نخورده باشد.**
پس `EmploymentContract.is_insured` هم از همین نقطه اثر می‌گذارد.

`Payslip.insurance_applies` در لحظهٔ محاسبه ثبت می‌شود. اگر بعداً این تیک عوض
شود، لیستی که قبلاً به تأمین اجتماعی رفته تغییر نمی‌کند.

### حق تأهل

برخلاف حق اولاد، حق تأهل **قانونی نیست** — سیاست شرکت است. مبلغش در «تنظیمات
سال مالی ← حق تأهل ماهانه» ثبت می‌شود و:

- فقط به پرسنلی می‌رسد که وضعیت تأهلشان «متأهل» است
- مثل حق مسکن و بن به نسبت روز کارکرد تسهیم می‌شود
- **صفر یعنی این قلم را ندارید** و سطرش اصلاً روی فیش نمی‌آید

تعداد فرزند در آن دخالتی ندارد؛ متأهلِ بدون فرزند هم مبلغ کامل را می‌گیرد.

> **حق اولاد فرق دارد:** مبنایش **حداقل دستمزد روزانه** است (طبق قانون
> `۳ × حداقل دستمزد روزانه` برای هر فرزند)، نه مزد روزانهٔ خود پرسنل. یعنی
> کسی که مزدش بالای حداقل است، حق اولادش با بقیه یکی است.

### ساخت قلم حقوقی بدون کدنویسی

`SalaryComponent.calc_type = PARAMETRIC` یعنی قلمی که کارگزینی خودش ساخته است،
با یک قاعدهٔ سه‌جزئی:

```
مبلغ = مبنا × مقدار × ضریب
```

| مبنا | یعنی |
|---|---|
| حداقل دستمزد روزانه سال | `LegalParameter.min_daily_wage` همان سال |
| مزد روزانه خود پرسنل | دستمزد قرارداد، و اگر نداشت حداقل دستمزد — همان `ctx.daily_base` حقوق پایه |
| مبلغ ثابت | عدد ثابتِ خود قلم |
| مبلغ یک قلم دیگر | مبلغ محاسبه‌شدهٔ قلم مبنا در همان فیش |

| مقدار | یعنی |
|---|---|
| روز کارکرد قابل پرداخت | ضرب در روزهای کارکرد |
| به نسبت کارکرد ماه | × کارکرد ÷ طول ماه — برای مبالغ ماهانه‌ای که باید تسهیم شوند |
| ثابت | بدون ضرب در کارکرد |

**چرا زبان فرمول نیست.** یک عبارت آزاد که کاربر می‌نویسد نه تست می‌شود نه ممیزی،
و ارزیابی‌اش در زمان اجرا یعنی هر غلط تایپی می‌تواند به فیش برسد. با این سه جزء،
هر ترکیب ممکن از پیش پیاده و تست شده است و همچنان **هر عدد توضیح خودش را دارد**:

> کمک هزینه ایاب و ذهاب: ۳٬۰۰۰٬۰۰۰ ریال حداقل دستمزد روزانه × ۲۳٫۷۲ روز کارکرد × ضریب ۰٫۲۵

**محاسبهٔ آزمایشی.** صفحهٔ ویرایش قلم، مبلغ را روی یک ماه نمونه (کارکرد و مزد
روزانهٔ واقعیِ همان شرکت) نشان می‌دهد — پیش از آنکه قلم وارد فیش کسی شود. این
پیش‌نمایش **همان تابع موتور** را صدا می‌زند، نه یک پیاده‌سازی دوم؛ اگر عددی صفر
شود، به‌جای کادر خالی می‌گوید چرا. `apps/payroll/engine/preview.py`.

**قلمی که به قلم دیگری بسته است** باید ترتیب بزرگ‌تری داشته باشد، وگرنه هنگام
محاسبه مبنایش هنوز صفر است. فرم همین را اعتبارسنجی می‌کند و اجازهٔ ذخیره نمی‌دهد.

**فیش قفل‌شده تغییر نمی‌کند.** هر سطر فیش مبنا، تعداد و ضریبِ لحظهٔ محاسبه را
جداگانه نگه می‌دارد (`PayslipLine.base_amount/quantity/rate`) به‌علاوهٔ متن
توضیح، پس عوض شدن ضریبِ قلم، گذشته را بازنویسی نمی‌کند.

قواعد پیچیده‌تر — بیمه، مالیات پلکانی، تخصیص پورسانت، اقساط — همچنان در کد
می‌مانند. آن‌ها مسئولیت قانونی دارند و جایشان جایی است که تست دارد.

### چارت سازمانی و تجمیع گزارش‌ها

سطوح: **سازمان › مرکز هزینه › واحد › پرسنل**. مرکز هزینه می‌تواند مرکز هزینهٔ
بالادست داشته باشد و واحد هم می‌تواند زیر واحد دیگری بنشیند، پس چارت واقعی هر
عمقی داشته باشد قابل بیان است.

**هر گره کد خودش را دارد** و کد کامل از زنجیرهٔ پدرانش ساخته می‌شود: مرکز هزینهٔ
`۱۰` و واحدِ `۵۰` زیرش، یعنی `۱۰-۵۰`. کد مرکز هزینه و واحد در **یک فضای مشترک**
یکتا هستند، وگرنه دو گرهٔ خواهر می‌توانستند کد کامل یکسان بگیرند. کد خالی موقع
ذخیره خودکار پر می‌شود (پله‌های ده‌تایی) تا دادهٔ قدیمی هم بی‌کد نماند.

**حلقه ممکن نیست:** گره نمی‌تواند زیرمجموعهٔ خودش شود — نه مستقیم و نه از راه
چند واسطه. حلقه یعنی آن شاخه از درخت بیرون می‌افتد و هزینه‌اش در هیچ گزارشی جمع
نمی‌شود؛ خطایی که فقط وقتی کشف می‌شد که جمع‌ها نخوانند.

**تجمیع روی هر سطح** یعنی جمع همهٔ فیش‌های زیر آن گره، نه فقط فیش‌های خودش:

- `/reports/<دوره>/org/` — هزینهٔ حقوق روی کل چارت، سطر به سطر. جمع سطرهای سطح
  اول دقیقاً برابر جمع کل دوره است، و فیشی که واحدش از چارت حذف شده در سطر
  «خارج از چارت فعلی» می‌آید تا این تساوی بی‌سروصدا نشکند.
- لیست بیمه، لیست مالیات و فایل بانک، هرکدام یک انتخاب‌گر گره دارند. **فایل
  اکسل همان گره را می‌گیرد** که روی صفحه انتخاب شده، وگرنه کاربر فیلتر می‌کند و
  فایلِ کامل تحویل می‌گیرد.
- چاپ دسته‌ای فیش هم روی گره فیلتر می‌شود: انتخاب یک مرکز هزینه، فیش همهٔ
  واحدهای زیرش را می‌آورد.

مبنای تجمیع، `Payslip.department` است — عکسِ لحظهٔ محاسبه. اگر فردا واحدی زیر
مرکز هزینهٔ دیگری برود، **گزارش ماه‌های گذشته عوض نمی‌شود**؛ فقط درخت امروز
تغییر می‌کند.

واحدی که هنوز مرکز هزینه ندارد گم نمی‌شود: در ریشهٔ درخت می‌آید و هم در صفحهٔ
چارت و هم در گزارش با هشدار دیده می‌شود.

### فیش حقوقی

**مبنای بیمه و مبنای مالیات روی فیش چاپ نمی‌شوند** (فیش A5، صفحهٔ فیش، پرتال).
خود مقادیر در `Payslip` می‌مانند چون گزارش بیمه و مالیات به آن‌ها تکیه دارند.

کنار محل امضا این متن چاپ می‌شود:

> موارد محاسباتی حقوق و مزایای مندرج در این فیش به‌صورت الکترونیکی رؤیت گردید و
> واریز خالص پرداخت به حساب شماره مندرج در فیش مورد تأیید قرار گرفت.

همین متن در پرتال کارکنان هم درست بالای دکمهٔ «فیش را تأیید می‌کنم» می‌آید —
آن‌جا متنی است که پرسنل با زدن دکمه می‌پذیرد.

## آنچه نیست (فازهای بعد)

فایل DSK تأمین اجتماعی و ثبت کد رهگیری · ورود کارکرد از فایل اکسل و دستگاه حضور و
غیاب · عیدی، سنوات و تسویه‌حساب · فیش اصلاحی · گردش تأیید درخواست مرخصی (ثبت
مستقیم کارگزینی هست، تأیید مرحله‌ای نیست) · احراز هویت دومرحله‌ای.

## دو نکته‌ای که باید با حسابدار شرکت تأیید شود

۱. **کسر بیمهٔ سهم کارگر از درآمد مشمول مالیات** — پرچم
   `LegalParameter.deduct_insurance_from_tax_base` (فعلاً فعال). مستقیماً روی مبلغ
   مالیات اثر دارد.

۲. **همپوشانی قراردادها** — MySQL معادل `EXCLUDE` constraint ندارد، پس این قاعده در
   `EmploymentContract.clean()` پیاده شده است. هر مسیر جدیدی که قرارداد می‌سازد باید
   حتماً `full_clean()` را صدا بزند.
