# بک‌تست تیر ۱۴۰۵ — سامانه در برابر فیش‌های واقعی

فیش‌های قطعیِ تیر ۱۴۰۵ (۳۳ نفر) از فایل اکسل شرکت وارد سامانه شد، دوره محاسبه
شد، و هر قلم کنار ستون متناظرش گذاشته شد.

```bash
python tools/load_excel_month.py 1405.xlsx "تیر 1405"
python tools/compare_excel_platform.py 1405.xlsx "تیر 1405"
```

**فقط ورودی‌ها بارگذاری می‌شوند، نه جواب‌ها.** مزد روزانه، کارکرد، ساعت
اضافه‌کاری، روز مأموریت، پورسانت خام و کسورات وارد می‌شوند؛ حقوق ثابت، بیمه،
مالیات و خالص را خودِ موتور می‌سازد.

---

## نتیجه پس از رفع سه مورد اول

| | |
|---|---|
| قلمی که ۳۳ از ۳۳ می‌خواند | **۱۳** |
| فیشی که ریال‌به‌ریال یکی است | **۲۲ از ۳۳** |
| اختلاف باقی‌مانده | فقط زنجیرهٔ تخصیص پورسانت (۱۱ نفر فروش) |

**هر ۲۲ نفر گروه پشتیبانی کامل می‌خوانند** — ناخالص، ماخذ بیمه، ماخذ مالیات،
کسورات و خالص، همه بدون یک ریال اختلاف. یازده نفر باقی‌مانده همگی گروه فروش‌اند
و تنها اختلافشان `پورسانت یک` است که هنوز زنجیرهٔ تخصیصش پیاده نشده.

اقلامی که کامل می‌خوانند: حقوق ثابت · پایه سنوات · مابه‌التفاوت سنوات · حق
مسکن · حق اولاد · حق تأهل · وجه بن · **اضافه‌کاری** · **حق مأموریت** ·
پورسانت دو و سه · کسر کار · کسر انبار

## نتیجهٔ اولیه (پیش از رفع)

| | تعداد قلم |
|---|---|
| کامل می‌خواند (۳۳ از ۳۳ نفر) | **۹** |
| نمی‌خواند | ۴ + پیامدهایشان |

**۵ فیش از ۳۳ فیش ریال‌به‌ریال یکی است** — و هر پنج نفر دقیقاً همان‌هایی‌اند که
اضافه‌کاری، مأموریت و پورسانت ندارند. یعنی **هستهٔ محاسبه درست است** و
اختلاف‌ها همگی در چهار قلم متغیرند.

### آنچه موتور خودش می‌سازد و درست می‌سازد

| قلم | نتیجه |
|---|---|
| حقوق ثابت | ۳۳/۳۳ ✓ |
| حق مسکن | ۳۳/۳۳ ✓ |
| حق اولاد | ۳۳/۳۳ ✓ |
| حق تأهل | ۳۳/۳۳ ✓ |
| وجه بن | ۳۳/۳۳ ✓ |

> حق تأهل تا دو هفته پیش اصلاً روی فیش نمی‌آمد. حالا ۳۳ از ۳۳ می‌خواند.

### آنچه فقط عبور می‌کند (ورودی دستی، نه محاسبه)

مابه‌التفاوت سنوات، پورسانت دو، پورسانت سه، کسر کار. این‌ها به‌صورت «مبلغ
دستی» وارد شده‌اند، پس یکی بودنشان آزمونِ فرمول نیست — فقط نشان می‌دهد مسیر
ورودی دستی سالم است.

## چهار اختلاف، و ریشهٔ هرکدام

### ۱) اضافه‌کاری — مبنای ساعتی فرق دارد (۱۵ نفر، ۳٪)

```
اکسل   : (مزد روزانه×۳۰ + سنوات روزانه×کارکرد) ÷ ۲۲۰ × ۱٫۴
سامانه : (مزد روزانه ÷ ۷٫۳۳) × ۱٫۴
```

نمونه (حامد عبادی): اکسل ۵٬۵۴۵٬۲۴۸ · سامانه ۵٬۳۷۷٬۰۳۱ · اختلاف ۳٫۰۳٪ کمتر.

جمع اختلاف در کل ماه: **−۱٬۳۳۵٬۴۱۸ ریال**. اختلافی یکنواخت و یک‌جهته است، پس
با اصلاح مبنا کامل بسته می‌شود.

### ۲) حق مأموریت — نرخ در سامانه ماهانه است، در فایل شخصی (۲۴ نفر)

```
اکسل   : روز × (مزد روزانه + پایه سنوات روزانه) × ضریب
         ضریب = ۲ برای واحد فروش، ۱ برای پشتیبانی
سامانه : روز × «مبنای روزانهٔ این ماه» × ضریب قلم
```

مبنای سامانه یک عدد برای همه است، ولی در فایل برای هر نفر فرق می‌کند چون به
مزد خودش بسته است. با پیکربندی قابل بیان نیست.

جمع اختلاف: **−۱٬۷۴۶٬۶۴۰٬۷۵۷ ریال** (بزرگ‌ترین اختلاف).

### ۳) پایه سنوات — سابقهٔ قبلی (۱ نفر)

سید کمیل حجازی از ۱۴۰۴/۱۰/۰۱ شروع کرده، پس سامانه سابقه‌اش را زیر یک سال
می‌بیند و پایه سنوات نمی‌دهد. اکسل ۵٬۱۶۶٬۶۷۷ می‌دهد، چون در همان کارگاه سابقهٔ
قبلی دارد.

رضا پیرایش با **همان تاریخ شروع** در اکسل هم صفر می‌گیرد — یعنی تفاوت واقعی
است، نه اشتباه تایپی.

این همان چیزی است که در `docs/PERSONNEL-AND-CONTRACT.md` بند ۵ آمده: تا وقتی
«سابقهٔ قبلی» فیلد نداشته باشد، قابل بیان نیست.

### ۴) پورسانت یک — زنجیرهٔ تخصیص (۱۱ نفر)

```
اکسل   : (پورسانت + مازاد ثابت) − (مابه‌التفاوت سنوات + ذخیره + کسر مازاد + مبلغ مأموریت)
سامانه : پورسانت خام
```

نمونه (سجاد منصور پور): اکسل ۹٬۰۳۶٬۴۶۱ · سامانه ۲۶۱٬۵۰۰٬۴۸۵.

## کشف ساختاری: اضافه‌کاری و مأموریتِ گروه پشتیبانی **ورودی نیستند، خروجی‌اند**

این مهم‌ترین چیزی است که بک‌تست نشان داد. ستون‌های فیش با ستون‌های «واقعی» یکی
نیستند:

| | گروه فروش (۱۱ نفر) | گروه پشتیبانی (۲۲ نفر) |
|---|---|---|
| ساعت اضافه‌کاری فیش | `= اضافه کار واقعی` | `= محاسبه اضافه کار` ← از زنجیرهٔ مازاد |
| روز مأموریت فیش | عدد دستی | `= محاسبه مدت ماموریت` ← از زنجیرهٔ مازاد |
| ضریب مأموریت | **۲** | **۱** |

یعنی برای دو-سوم پرسنل، «اضافه‌کاری» و «مأموریت» ساعت و روزِ کارکرده نیستند؛
شکلی‌اند که **مازاد ثابت** در آن پرداخت می‌شود. در هر پنج ماه فایل، این تفکیک
دقیقاً به همین شکل است.

در بار اول این ستون‌ها اشتباه خوانده شدند («واقعی» به‌جای فیش) و اختلاف
اضافه‌کاری ۳۶۵ میلیون درآمد. با ستون درست، همان اختلاف به ۱٫۳ میلیون رسید.

| | اکسل | سامانه | اختلاف |
|---|---|---|---|
| ناخالص | ۱۱٬۶۴۰٬۸۸۸٬۵۴۸ | ۱۱٬۵۳۵٬۰۲۶٬۱۳۳ | −۱۰۵٬۸۶۲٬۴۱۵ |

اختلاف حدود **۰٫۹٪** است و همه‌اش از همان چهار قلم می‌آید. سه‌تای اول با تغییر
کوچک بسته می‌شوند؛ چهارمی (زنجیرهٔ تخصیص) کار بزرگ‌تری است.

## آنچه برای رفع ۱ تا ۳ انجام شد

هیچ‌کدام سخت‌کد نشد؛ هر سه **انتخابی** شدند و پیش‌فرضشان رفتار قبلی سامانه است،
تا شرکت دیگری با روش دیگر خراب نشود.

| # | تغییر | کجا تنظیم می‌شود |
|---|---|---|
| ۱ | مبنای اضافه‌کاری | تنظیمات ← سال مالی ← «مبنای اضافه‌کاری» = حقوق و سنوات ماهانه ÷ ساعات کار ماهانه |
| ۲ | مبنای مأموریت | تنظیمات ← سال مالی ← «مبنای حق مأموریت» = مزد روزانه + پایه سنوات روزانه |
| ۳ | سابقه | فیلد «سابقهٔ قبلی (ماه)» روی پرسنل؛ سابقه دیگر ذخیره نمی‌شود |

ضریب ۲ مأموریتِ فروش با یک قلم دوم و دامنه شمول مرکز هزینه بیان شد — بدون
کدنویسی، همان‌طور که برای جمعه‌کاری هم بود.

### یک ایراد که همین‌جا پیدا شد

پس از اصلاح مبنای اضافه‌کاری، هنوز چند هزار ریال اختلاف روی ۹ نفر می‌ماند.
علتش این بود که موتور `overtime_hours` را می‌خواند که **دو رقم اعشار** دارد:
۲۷۴ دقیقه می‌شد ۴٫۵۷ ساعت به‌جای ۴٫۵۶۶۶…، و با نرخ میلیونیِ هر ساعت همان دو
رقم چند هزار ریال خطا می‌ساخت. موتور حالا از دقیقه می‌خواند — همان قاعده‌ای که
از اول بالای مدل کارکرد نوشته شده بود ولی رعایت نمی‌شد.

با این یکی، اضافه‌کاری از ۲۴ به **۳۳ از ۳۳** رسید.

### «کسر انبار»

پنج نفر پشتیبانی فقط به‌خاطر این قلم نمی‌خواندند. سامانه چنین قلمی نداشت و
**بدون یک خط کد** ساخته شد (کسورات، ورود دستی). حالا آن ۵ نفر هم می‌خوانند.

## بازتولید

دیتابیس `payroll_tir` جداست و به کپی دیتابیس سرور دست نمی‌زند:

```bash
mysql -uroot -e "DROP DATABASE IF EXISTS payroll_tir;
  CREATE DATABASE payroll_tir CHARACTER SET utf8mb4 COLLATE utf8mb4_persian_ci;"
python manage.py migrate && python manage.py setup_operational
python tools/load_excel_month.py 1405.xlsx "تیر 1405"
python tools/compare_excel_platform.py 1405.xlsx "تیر 1405"
```

هر ماه دیگری هم با همین دو دستور قابل آزمون است.
